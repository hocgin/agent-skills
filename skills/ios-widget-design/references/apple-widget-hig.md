# Apple Widgets HIG：iOS/iPadOS 决策指南

本文件是对 Apple [Widgets Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/widgets) 的决策性归纳，供 `ios-widget-design` Skill 使用。它不是规范原文；如果本文件与 Apple 的现行文档或目标系统行为不一致，以 Apple 文档为准。

已核对：2026-08-25。适用范围：iOS 与 iPadOS 的 WidgetKit 小组件，包括主屏幕、Today View、锁定屏幕和 StandBy。

## 1. 核心判断

- 小组件应提供及时、可一瞥读懂的信息，或与内容直接相关的轻量功能。先回答“用户此刻最想知道或完成什么”，再决定视觉形式。
- 用一个主信息建立层级；再加入少量直接支持它的内容。空得像应用图标没有价值，密得像仪表盘则失去可读性。
- 让内容在一天中有合理的新鲜感，但不要承诺实时或按分钟刷新。短时间内需要频繁更新的进度或事件应考虑 Live Activity。
- 仅支持有价值的尺寸。小尺寸通常承载一个关键事实；中、大尺寸可以扩展范围、趋势、详情或少量行动，而不是简单放大。
- 品牌色、字体或自定义图形可以辅助识别，但不应压过信息。除多来源内容等少数情形外，不要把 Logo 或 App 图标当作主要内容。

## 2. 家族与系统情境

| 情境 | 应优先解决的问题 | 设计约束 |
| --- | --- | --- |
| 主屏幕 / Today View | 让人快速了解状态并进入对应详情 | 系统家族可使用 full-color 或 accented 呈现；要测试浅色、深色、透明（clear）和着色（tinted）外观。 |
| 锁定屏幕 | 提供有用的极简状态，而非额外的启动器 | iPhone/iPad 可用 inline、circular、rectangular accessory；它们采用 vibrant 呈现。inline 只有一个可点击目标。Always-On 时亮度降低。 |
| StandBy | 从更远距离读取关键内容 | 两个 small system 小组件会并排且放大；优先大字和强层级，少依赖丰富图像或颜色传意，背景应能自然融入黑色环境。低光下会变为红色单色调。 |

在 iPhone/iPad 上不要规划 `accessoryCorner`，它是 Apple Watch complication 的形状。若需要支持多尺寸，请为每个尺寸明确：主信息、可见次级信息、点击后的目标、无数据状态。具体 WidgetKit 家族、可用平台和点数请查阅 [小组件类型与尺寸](widget-dimensions.md)，不要把一个设备上的数值当成通用尺寸。

## 3. 信息、行动与状态

- 只显示直接服务于小组件主目的的信息。大尺寸可以提供更多数据或更细的图形，但焦点不变。
- 交互元素应少而明确。按钮、开关和链接只用于与当前内容直接相关的简单动作；复杂任务留在 App 内。
- 非交互区域的点击应深链到与当前信息对应的详情或行动，而不是只打开 App 首页。
- 为登录、空内容、错误、过期数据和加载状态设计简洁且诚实的反馈。若登录会带来额外价值，明确说明价值，而非只显示“请登录”。
- 预览与占位符都是产品体验的一部分：Gallery 预览应真实展示每个尺寸的能力；加载时用稳定的界面框架加半透明形状表达将出现的动态内容。不要把随机或误导性内容当占位符。
- Gallery 描述使用简洁、自然的句式，以动作动词开头，例如“查看某地点的当前天气和预报”。同一小组件的多种尺寸应分组并共用一条描述。

## 4. 布局、文字与形状

- 默认采用系统标准边距。大多数小组件为 **16 pt**；只有在为图形、按钮、背景形状建立紧凑分组时，才考虑 **11 pt**。锁定屏幕与 StandBy 的边距更小，优先让系统处理。
- 视觉稿和设计标注必须注明目标设备的屏幕点数；iPadOS 还要注明 Apple 表中使用的是 `Canvas` 还是 `Device`。精确对照表位于 [小组件类型与尺寸](widget-dimensions.md)。
- 不要为了贴合边缘而盲目移除内容边距，也不要依赖固定像素尺寸。让 SwiftUI 和系统在设备及缩放因子间自适应。
- 内容的圆角需与小组件容器协调；SwiftUI 实现应使用 `ContainerRelativeShape`，而不是猜测固定圆角半径。
- 优先系统字体、文本样式与 SF Symbols；这能保证跨平台一致性和与文字的对齐。自定义字体只能少量使用，并须在一瞥时可读。
- 正文通常不小于 **11 pt**。使用真实 `Text` 而非位图文字，以支持缩放与 VoiceOver。系统字体或 `custom(_:size:)` 能支持从 Large 到 AX5 的 Dynamic Type。

## 5. 颜色与渲染模式

不要只为全彩设计。iPhone/iPad 的主屏幕和 Today View 可能在 full-color 或 accented 下展示；锁定屏幕和低光 StandBy 使用 vibrant。三个模式都要保持层级和可读性。

| 模式 | 系统行为 | 设计做法 |
| --- | --- | --- |
| `fullColor` | 系统不修改视图颜色 | 支持浅色与深色，优先语义色或资产目录颜色变体。 |
| `accented` | 背景会被移除或替换为系统的着色 / Liquid Glass 效果；视图分为 primary 与 accent 两组 | 先定义不依赖原色的层级；只把真正需要强调的内容放入 accent 组。用 `widgetAccentable(_:)` 明确分组，并在 clear 与 tinted 外观检查。 |
| `vibrant` | 锁定屏幕和低光 StandBy 会把内容去色并基于背景形成动态的单色效果 | 使用不透明的灰阶资产；较亮的白/浅灰放主信息，较深灰放次要信息。不要用半透明白代替灰阶；检查图片和文字在灰阶与低亮度下的对比。 |

- 颜色只可强化层级或情绪，不得单独承担状态、趋势、成功/失败等语义；同时提供文字、图标或形状线索。
- tinted 与 clear 外观会默认去饱和全彩图像。保留全彩图像只适合专辑封面等媒体内容，且图像应小于小组件本身，避免破坏系统感。
- 在低光 StandBy、Always-On 与各种壁纸上验证对比度；“默认好看”的全彩方案不等于这些情境中仍可读。

## 6. 最终审查清单

在提交视觉稿、设计规范或实现前检查：

- [ ] 每个尺寸都表达同一目的，但能提供与尺寸相称的新价值。
- [ ] 一眼可读的主信息明确，次要内容没有挤压它。
- [ ] 每一个交互都有直接相关的结果与正确的深链；没有把小组件做成迷你 App。
- [ ] light、dark、clear、tinted、vibrant、Always-On 与 StandBy（如支持）下仍有层级与对比。
- [ ] 不依赖颜色传达语义；文字真实可访问、系统可缩放，且一般不低于 11 pt。
- [ ] 边距、圆角、文字与符号遵循系统容器和 SwiftUI 的自适应行为。
- [ ] Gallery 预览、加载占位符、无数据和登录状态与实际体验一致。
- [ ] 频繁、实时的更新需求没有被错误地承诺给普通小组件。
